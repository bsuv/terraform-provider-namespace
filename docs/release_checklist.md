# Terraform Registry Publishing & Release Checklist

This document provides the authoritative, step-by-step operational runbook for releasing and publishing the `terraform-provider-namespace` provider to the [Terraform Registry](https://registry.terraform.io).

---

## 1. Release Architecture & Protocol Compliance

The Namespace Terraform Provider conforms to the **Terraform Registry Provider Protocol v6**. To be accepted by the registry and consumable by Terraform CLI >= 1.11.0, every release must emit:

1. **Versioned Binaries inside Archives**: The binary within each archive must be named `terraform-provider-namespace_v<VERSION>` (e.g. `terraform-provider-namespace_v0.1.0`).
2. **Deterministic Zip Archives**: Cross-compiled `.zip` files named `terraform-provider-namespace_<VERSION>_<OS>_<ARCH>.zip` for every supported OS/architecture pair declared in `.goreleaser.yml` (Linux, Darwin, Windows, and FreeBSD across their configured `amd64`, `arm64`, `arm`, and `386` targets and exclusions).
3. **Standalone Registry Manifest**: A standalone root release asset named `terraform-provider-namespace_<VERSION>_manifest.json` declaring Protocol 6 support.
4. **SHA256 Checksums**: A `terraform-provider-namespace_<VERSION>_SHA256SUMS` file containing SHA-256 digests for all `.zip` archives and the standalone `manifest.json`.
5. **Detached GPG Signature**: A cryptographic signature `terraform-provider-namespace_<VERSION>_SHA256SUMS.sig` generated by the publisher's registered GPG signing key.
6. **Documentation**: Registry documentation automatically ingested from the `docs/` directory.

## 2. One-Time Setup & Prerequisites

### 2.1. GitHub Repository Configuration
- Repository name must follow standard naming: `terraform-provider-namespace` under the `bsuv` GitHub account.
- GitHub Actions CI must be active on `main` branch.
- Create protected GitHub environments named `acceptance` and `release`. Restrict deployments to the intended branch/tag rules and require reviewer approval for release deployments. Store live Namespace credentials only in `acceptance`; store signing credentials only in `release`.
- Enable GitHub private vulnerability reporting before making the repository public and verify that the advisory link in `SECURITY.md` is reachable from a non-maintainer account.
- Before changing repository visibility, fetch every branch, tag, and pull-request ref and require `scripts/secret-scan.sh --all-refs` to pass. If a retired GitHub-managed ref still contains a finding, keep the repository private and recreate it from the clean release ancestry; rewriting only `main` does not purge retained pull-request refs. Never suppress an actual credential or private-key fixture to make this gate pass.

### 2.2. Pinned Release Toolchain

- Use Go 1.26.7 for all mandatory build, test, and release gates. The scheduled current-dependencies lane separately exercises Go 1.27.x.
- Use GoReleaser 2.17.1 for configuration checks, snapshots, and releases.
- Use Gitleaks 8.30.0 for secret scanning. Linux x86_64 CI installs the checksum-pinned binary with `scripts/install-gitleaks.sh`; other platforms must install the same version directly. The scan intentionally rejects missing or different versions.

### 2.3. GPG Key Generation & Export
1. Generate a dedicated 4096-bit RSA GPG key (**Note**: The Terraform Registry signing ingestion service strictly requires **RSA** (>= 2048-bit, 4096-bit recommended) or DSA keys. Elliptic Curve keys—including **ECC, Ed25519, and ECDSA—are unsupported** by the Terraform Registry and will cause registry ingestion/verification failure). Use the interactive flow and protect the key with a unique, strong passphrase; never generate an unprotected release key:
   ```bash
   gpg --full-generate-key
   ```
   Select RSA, 4096 bits, an appropriate expiry, a dedicated publisher-controlled identity, and a passphrase held in the release secret manager. Record the exact identity in `GPG_SIGNING_IDENTITY`; for example:
   ```bash
   GPG_SIGNING_IDENTITY="Namespace Terraform Provider Releases <publisher-controlled-email>"
   ```
2. Retrieve the GPG Key ID and Fingerprint:
   ```bash
   KEY_ID=$(gpg --list-secret-keys --keyid-format LONG "${GPG_SIGNING_IDENTITY}" | grep sec | awk '{print $2}' | cut -d/ -f2)
   FINGERPRINT=$(gpg --fingerprint "${GPG_SIGNING_IDENTITY}" | grep -A 1 "Key fingerprint" | tail -1 | tr -d ' ')
   ```
3. Export the ASCII-armored public key:
   ```bash
   gpg --armor --export "${KEY_ID}" > namespace-provider-public-key.asc
   ```
4. Export the ASCII-armored private key for GitHub Secrets:
   ```bash
   gpg --armor --export-secret-keys "${KEY_ID}"
   ```

### 2.4. Terraform Registry Signing Key Registration
1. Sign in to [registry.terraform.io](https://registry.terraform.io) using the `bsuv` GitHub publisher account.
2. Navigate to **Settings -> Signing Keys -> Add Key**.
3. Paste the ASCII-armored public key (`namespace-provider-public-key.asc`).
4. Copy the resulting Key ID and verify it matches your GPG fingerprint.

### 2.5. GitHub Environment Secrets Configuration
Configure the following secrets on the protected `release` environment under `Settings -> Environments -> release`:
- `GPG_PRIVATE_KEY`: The exported ASCII-armored private key.
- `PASSPHRASE`: Passphrase for the private key.
- `GPG_FINGERPRINT`: The 40-character GPG fingerprint.

Configure the `NSC_*` credentials and deterministic fixture values listed in `TEST_READY.md` on the protected `acceptance` environment. Do not duplicate either credential set as repository-wide secrets.

## 3. Pre-Release Verification Checklist

Execute the full suite of local quality gates before tagging a release:

- [ ] **1. Code Formatting Gate**:
  ```bash
  test -z "$(gofmt -l .)"
  ```

- [ ] **2. Terraform Formatting Gate**:
  ```bash
  terraform fmt -check -recursive .
  # Must return 0 errors
  ```

- [ ] **3. Static Analysis & Linter Gate**:
  ```bash
  go vet ./...
  golangci-lint run ./...
  go run github.com/rhysd/actionlint/cmd/actionlint@v1.7.12
  shellcheck scripts/*.sh
  ```

- [ ] **4. Unit & API Contract Tests**:
  ```bash
  go test -v -race -count=1 ./...
  python3 -m unittest -v scripts/test_acceptance_report_generator.py
  ```

- [ ] **5. Dependency, Vulnerability, and Secret Gates** (with Go 1.26.7):
  ```bash
  go mod tidy
  git diff --exit-code go.mod go.sum
  go mod verify
  go run golang.org/x/vuln/cmd/govulncheck@v1.7.0 ./...
  git fetch --force origin \
    '+refs/heads/*:refs/remotes/origin/*' \
    '+refs/tags/*:refs/tags/*' \
    '+refs/pull/*/head:refs/remotes/origin/pull/*'
  bash ./scripts/secret-scan.sh --all-refs
  ```

- [ ] **6. Documentation Generation & Diff Check**:
  ```bash
  go run github.com/hashicorp/terraform-plugin-docs/cmd/tfplugindocs generate --provider-name namespace --rendered-provider-name "Namespace Cloud"
  git diff --exit-code docs/
  go run github.com/hashicorp/terraform-plugin-docs/cmd/tfplugindocs validate --provider-name namespace
  ```

- [ ] **7. GoReleaser Configuration Check**:
  ```bash
  # Use exactly GoReleaser 2.17.1.
  goreleaser check
  # Must pass with 1 configuration file(s) validated
  ```

- [ ] **8. GoReleaser Snapshot Artifact Smoke Test**:
  ```bash
  goreleaser release --snapshot --clean --skip=publish,sign
  SNAPSHOT_DIR="$(mktemp -d)"
  trap 'rm -rf "${SNAPSHOT_DIR}"' EXIT
  ./scripts/stage-goreleaser-snapshot.sh dist "${SNAPSHOT_DIR}"
  ./scripts/smoke-test.sh --dist-dir "${SNAPSHOT_DIR}" --allow-unsigned-snapshot
  # Must pass with "Clean-install smoke test PASSED successfully!"
  ```

  `--allow-unsigned-snapshot` is deliberately restricted to versions containing `SNAPSHOT`. Never use it to validate a tagged release; the release workflow requires and verifies the detached GPG signature.

- [ ] **9. Acceptance Test Suite (Staging / Testbed)**:
  ```bash
  TF_ACC=1 go test -v -json -count=1 -timeout 120m ./internal/provider/... -run '^TestAcc' > acceptance.json
  ./scripts/generate-acceptance-report.sh \
    --input acceptance.json \
    --commit-sha "$(git rev-parse HEAD)" \
    --run-id "${GITHUB_RUN_ID}" \
    --run-link "https://github.com/bsuv/terraform-provider-namespace/actions/runs/${GITHUB_RUN_ID}" \
    --tf-version "$(terraform version -json | jq -r .terraform_version)" \
    --suite full
  ```
  This gate is authoritative only in the protected GitHub Actions environment with the dedicated test tenant, deterministic fixtures, partner token, and trusted-authority JWT. Do not publish from an ad-hoc local result that lacks immutable workflow provenance.

## 4. Release Execution Procedure

### Step 1: Update CHANGELOG
Update `CHANGELOG.md` with release notes, highlighting:
- New Features & Resources
- Enhancements & Schema Additions
- Bug Fixes & Breaking Changes
- Protocol & Registry compatibility

### Step 2: Create Semantic Version Git Tag
Create an annotated git tag starting with `v` matching SemVer:
```bash
RELEASE_VERSION="v0.1.0"
git tag -a "${RELEASE_VERSION}" -m "Release ${RELEASE_VERSION}"
git push origin "${RELEASE_VERSION}"
```

### Step 3: Monitor Release CI Workflow
1. Navigate to GitHub Actions -> `release.yml`.
2. Verify GoReleaser completes:
   - Builds every OS/architecture target declared in `.goreleaser.yml` with `CGO_ENABLED=0`.
   - Packs `.zip` archives containing `terraform-registry-manifest.json`, `LICENSE`, and `README.md`.
   - Generates standalone `terraform-provider-namespace_${VERSION}_manifest.json`.
   - Generates `terraform-provider-namespace_${VERSION}_SHA256SUMS` and `terraform-provider-namespace_${VERSION}_SHA256SUMS.sig`.
   - Attaches the sanitized acceptance report, JUnit result, and sanitized test log produced for the exact tagged commit.
   - Creates GitHub Release and uploads all assets.

## 5. Post-Release Registry Ingestion & Verification

### Step 1: Verify Registry Ingestion
1. Terraform Registry automatically detects the GitHub release tag via webhook.
2. Visit `https://registry.terraform.io/providers/bsuv/namespace/<VERSION>`.
3. Verify that:
   - Version status is marked **Published**.
   - GPG signature verification status is **Verified**.
   - Documentation for all resources, data sources, and ephemeral resources renders properly.

### Step 2: Production Smoke Test
Create a clean workspace outside the repository and verify download from the live registry:
```bash
cat << 'EOF' > main.tf
terraform {
  required_version = ">= 1.11.0"
  required_providers {
    namespace = {
      source  = "bsuv/namespace"
      version = "0.1.0"
    }
  }
}

variable "namespace_token" {
  type      = string
  sensitive = true
  ephemeral = true
}

provider "namespace" {
  token = var.namespace_token
}

data "namespace_github_base_images" "linux" {
  labels = ["ubuntu-24.04"]
}
EOF

terraform init
terraform validate
```

## 6. Troubleshooting & Rollback

- **Registry reports "Invalid Manifest"**: Verify that `terraform-registry-manifest.json` contains `{"version": 1, "metadata": {"protocol_versions": ["6.0"]}}` and that the standalone manifest asset is named `terraform-provider-namespace_<VERSION>_manifest.json`.
- **GPG Signature Mismatch / Bad Signature**: Ensure `GPG_FINGERPRINT` in GitHub Secrets matches the public key uploaded to Terraform Registry, and that `SHA256SUMS` was signed with `--detach-sign`.
- **Accidental Bad Release**:
  1. Terraform Registry does **not** allow replacing an existing version tag.
  2. If a broken release was published, prepare a hotfix patch (e.g. `v0.1.1`), complete all verification checks, and publish the new patch tag.
  3. Optionally, mark the compromised or defective release version as *deprecated* or *yanked* in the Terraform Registry settings.
